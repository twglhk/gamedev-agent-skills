# B. Genre-breaking core constraint

## B1. Define the core constraint

- [ ] **List five things the genre takes for granted.** Example, turn-based RPG: HP bars, turn order and initiative, gear stat farming, town shops, grinding weak enemies.
  - For a hybrid, list each parent genre separately. Example, auto-battler: shop rerolls, star merging, synergy table, round health, item combining. Narrative exploration RPG: dialogue choices, skill-check dice, quest log, inventory, XP levels. Mark which ones your game carried over unchanged.
- [ ] **Pick one constraint that removes or flips one of them to the extreme.** Examples: no movement controls; enemy health is hidden; you can only move units, never damage them; time passes only when the player moves.
  - Propose several candidates; the human picks one. It must be "none at all" or "reversed", not "a bit less".
- [ ] **Write the one-line rule:** "Our game is a [genre], but it has one absolute rule: [core constraint]."

## B2. Find and resolve the contradictions it creates

- [ ] **List what the constraint breaks right away.** Write three points where the game becomes trivial (too easy), unfair (too hard) or dull with the constraint in.
- [ ] **Design a new mechanic that meets the constraint head-on instead of working around it.** Don't retreat to familiar grammar (putting HP back, filling space with generic enemies); design an action only possible under this constraint. Into the Breach: every enemy attack is visible, so the game adds stationary targets (buildings) that can't dodge.
  - If the fix is "what TFT has" or "what Baldur's Gate has", you ran away. Ask whether the action only makes sense under this constraint.

## B3. Let the systems follow (self-designing)

- [ ] **Cut every system that's only there out of habit.** Menus, stats and inventory you meant to add because every RPG or action game has them go, if they don't serve the constraint.
  - Ask of each system: "Without this, does the core constraint shine less?" Anything answered "no" goes to the A1 kill list as a candidate.
- [ ] **Redefine win and loss.** Set game-over and clear conditions that come from the constraint (loss of the power grid instead of player death, failing to defend an object).
  - Ask whether your current win and loss conditions come from the constraint or from genre habit.

## B4. One-scenario paper or greybox test

- [ ] **Build the smallest greybox: one fight or one stage.** No art, no story; only the constraint rule working. Keep it separate from any larger prototype instead of bolting it on.
- [ ] **Test whether the fun grows by itself.** Watch whether players find tricks the designer didn't plan, using the constraint, and say "wait, that works?". Count how often that happens when the human plays it and record it in the design doc. Zero means the constraint is still decoration.
